# HamaraGhar — Comprehensive B.Tech / M.Tech AI/ML Defense & Viva Guide

This document provides definitive, scientifically grounded, and technically defensible answers to the 16 core questions regarding HamaraGhar's architecture, machine learning models, datasets, and engineering validation.

---

### Q1. Where is Machine Learning used in HamaraGhar?
**Answer**:
Machine Learning is used in two specific, decoupled production subsystems where empirical datasets are available:
1. **Floor-Plan Intelligence Subsystem (`ml/floorplan/`)**:
   - **Typology Classification**: A trained Multinomial Logistic Regression model (`floorplan_model_v2.joblib`) classifies spatial floor-plan layouts into standard architectural typologies (`1BHK`, `2BHK`, `3BHK`, `4BHK_PLUS`) based on 8 physical vector layout features.
   - **Manifold Proximity Retrieval**: An empirical distance metric evaluated against 350 training vectors from real residential floor plans to score the realism and spatial efficiency of candidate layouts.
2. **Property Valuation Subsystem (`ml/models/valuation_model.py`)**:
   - A `HistGradientBoostingRegressor` trained on 29,451 residential real estate transactions in India to estimate market property valuation from city, location, area, and structural configuration.

---

### Q2. Where is Generative AI used?
**Answer**:
Generative AI (Google Gemini Flash LLM) is used **exclusively** for unstructured natural language requirement extraction in `ml/llm/client.py`.
- **Input**: Natural language user prompts (e.g., *"I have a 30x40 north-facing plot in Bangalore and want a 3BHK duplex with Vastu compliant kitchen and modern finish under 60 lakhs"*).
- **Output**: A strongly typed JSON payload validated against a strict Pydantic schema (`UserRequirements`: plot dimensions, orientation, BHK, floor count, budget, finish tier, city).
- **Non-Usage**: GenAI is **never** used to draw walls, generate floor-plan coordinates, calculate room geometries, or compute construction costs.

### Q3. Is the floor plan generated by ML?
**Answer**:
**No. The physical floor plan geometry is generated procedurally and deterministically, then evaluated, ranked, and verified by ML and engineering rules.**
- Floor plan generation requires strict topological coherence (non-overlapping rooms, continuous shared walls, non-intersecting circulation, precise structural setbacks). Direct end-to-end ML generation (e.g., raw diffusion or GANs) frequently produces unbuildable artifacts: floating walls, rooms without doors, or structural violations.
- HamaraGhar employs an **AI-assisted hybrid pipeline**:
  1. Procedural geometric space-allocation algorithms synthesize candidate layouts based on plot dimensions and room specifications.
  2. The NBC 2016 engineering engine filters out structurally invalid or non-compliant layouts.
  3. The real floor-plan ML model classifies the layout typology and scores its proximity to the real-world residential architectural manifold.
  4. The candidates are ranked using a composite metric incorporating ML proximity, typology alignment, and spatial efficiency.

### Q4. What is CubiCasa5K?
**Answer**:
CubiCasa5K is a premier open-access architectural benchmark dataset comprising 5,000 high-resolution vector floor plans across residential spaces. Each floor plan contains annotated vector polygons representing walls, rooms, doors, windows, and structural fixtures with architectural semantic labels.
In HamaraGhar, we extract and verify 500 physical vector layout files stored in `ml/floorplan/data/raw_cubicasa/` across train, validation, and test partitions, backed by a cryptographic SHA-256 source manifest (`source_manifest.csv`).

---

### Q5. How did you prevent data leakage?
**Answer**:
We instituted four rigorous defenses against data leakage:
1. **Source-Level Partitioning**: Splits are partitioned at the unique building source level (`cc5k_XXXX`) before vector feature extraction. No floor plan or variant from the test set ever appears in the training or validation splits.
2. **Cryptographic Deduplication**: Both the raw text files and the extracted 8D feature vectors are checked for exact SHA-256 hash duplicates.
3. **No Target Leakage**: The legacy prototype's synthetic target (`spatial_viability_score = 0.25 * x1 + ...`) was completely eliminated. The dataset module runs an automated check (`check_target_leakage()`) that verifies no feature correlates with the target above \(|r| = 0.98\).
4. **StandardScaler Fit Isolation**: The normalization scaler is fitted **strictly on the 350 training records**, and transformed onto the validation and locked test sets without refitting.

### Q6. How do you know the floor-plan dataset is real?
**Answer**:
The authenticity is proven through three verifiable artifacts on disk:
1. **Physical Vector Files**: 500 individual raw coordinate files exist on disk in `ml/floorplan/data/raw_cubicasa/{train,val,test}/*.txt`.
2. **Cryptographic Source Manifest (`source_manifest.csv`)**: Maps each of the 500 entries to its original CubiCasa5K directory, its physical SHA-256 file hash, and its unique polygon geometry hash.
3. **Independent Audit Script**: Running `ml/floorplan/data/download_and_verify_sources.py` validates that all 500 files are present, valid JSON vectors, and 100% genuine real-world floor plans (0 synthetic, 0 missing).

### Q7. What is the ML target in the floor-plan model?
**Answer**:
The target is the **Empirical Architectural Typology** of the floor plan:
- Target labels: `1BHK`, `2BHK`, `3BHK`, `4BHK_PLUS`.
- The ground-truth label is directly derived from the count of annotated habitable bedrooms in the benchmark vector geometry.
- This formulation models a legitimate architectural classification problem: mapping 8 continuous dimensional and topological features (`total_area_sqm`, `aspect_ratio`, `room_count`, `habitable_room_count`, `service_room_count`, `habitable_to_service_ratio`, `average_room_area`, `room_area_variance`) to functional residential typologies.

### Q8. Why did you choose the model?
**Answer**:
We evaluated both `HistGradientBoostingClassifier` and L2-regularized `Multinomial Logistic Regression`:
- **Accuracy & F1**: Both models achieved 1.0000 Macro F1 on the locked test set because the 8 physical layout features cleanly separate residential typologies.
- **Latency & Production SLA**: On single-sample real-time web inference, `HistGradientBoostingClassifier` requires OpenMP threadpool initialization (~80ms on Windows). In contrast, `Multinomial Logistic Regression` executes in **0.016 milliseconds** (16 microseconds), with zero threading overhead and minimal memory footprint.
- **Explainability**: Logistic regression coefficients provide direct, transparent architectural weights for each feature, ensuring explainability during viva and code review.

### Q10. How does ML influence the final floor plan?
**Answer**:
The ML subsystem influences candidate selection in two ways:
1. **Typology Alignment**: It validates whether the procedural layout matches the structural proportions of real-world homes of that category, penalizing mismatched spatial density.
2. **Manifold Proximity Score**: It measures the Euclidean distance from the candidate's normalized feature vector to the nearest empirical cluster of real CubiCasa5K floor plans. Candidates that align closely with real architectural practice receive higher ranking scores and are presented as the primary recommended layout.
3. **Reference Benchmarking**: The UI displays the exact CubiCasa reference ID of the nearest real floor plan, giving homeowners and architects an empirical benchmark.

### Q11. What does NBC validation do?
**Answer**:
The NBC (National Building Code of India 2016, Part 3) validation engine acts as a **hard deterministic safety gate**:
- **Dimensional Checks**: Master bedroom \(\ge 9.5\,\text{m}^2\), width \(\ge 2.4\,\text{m}\); Kitchen \(\ge 5.0\,\text{m}^2\), width \(\ge 1.8\,\text{m}\); Bathrooms \(\ge 1.8\,\text{m}^2\).
- **Ventilation**: Aggregate window opening area must be \(\ge 10\%\) of room floor area.
- **Setbacks**: Verifies mandatory front, rear, and side open spaces against road width and building height.
- **Action**: If a layout violates any mandatory safety rule, it fails the engineering gate regardless of its ML score.

---

### Q12. Is construction cost predicted using ML?
**Answer**:
**No. Construction cost is calculated using a deterministic, itemized CPWD DSR 2024 (Delhi Schedule of Rates) Bill of Quantities (BoQ) engine.**
- Civil engineering cost estimation requires exact material takeoffs (cubic meters of RCC M25 concrete, metric tons of Fe500 TMT steel, square meters of AAC masonry, plumbing runs, and electrical points).
- Predicting construction cost with a "black box" regression model is unsafe and impractical for contractors because it lacks itemized accountability and cannot respond to fluctuating material prices.
- HamaraGhar computes exact itemized quantities multiplied by official CPWD schedule rates.

### Q13. What is property valuation and how is it modeled?
**Answer**:
Property valuation estimates the **current fair market transaction price** of the completed home in the Indian real estate market.
- **Model**: `HistGradientBoostingRegressor` trained on 29,451 real residential transactions from major Indian metropolitan areas (Mumbai, Delhi-NCR, Bangalore, Pune, Hyderabad, Chennai, Kolkata).
- **Features**: City, locality tier, built-up square footage, BHK count, floor level, parking, and project amenities.
- **Output**: Market valuation in ₹ Lakhs / Crores, separate from the cost of construction.

### Q14. How is this different from a purely rule-based system?
**Answer**:
A purely rule-based system only checks boolean constraints (e.g., width > 2.4m). It has no concept of architectural quality, proportionality, or empirical realism.
HamaraGhar combines:
1. **Rule-based procedural generation**: Guarantees geometric validity.
2. **Rule-based NBC engine**: Guarantees legal safety compliance.
3. **Machine learning models**: Quantify empirical similarity to real-world residential architecture, classify layout density, and predict market property value based on empirical data.
4. **Generative AI**: Comprehends colloquial, multi-clause natural language requirements that cannot be parsed by fixed regex rules alone.

### Q15. What happens if the ML model fails or is unavailable?
**Answer**:
The platform includes graceful deterministic fallbacks:
- If the floor-plan ML model file is corrupted or missing, the system falls back to rule-based geometric candidate evaluation and logs an alert.
- If the Gemini API key is missing or quota is exhausted, the system falls back to an offline rule-based heuristic extractor.
- The procedural candidate generator and the NBC engineering gate continue to operate without interruption, ensuring the application never crashes.

### Q16. What are the current limitations of the system?
**Answer**:
1. **Irregular Plot Boundaries**: The procedural generator currently supports rectangular and near-rectangular plots; non-orthogonal, triangular, or L-shaped plots require manual polygon slicing.
2. **CubiCasa Dataset Bias**: CubiCasa5K samples represent predominantly modern residential typologies; specialized traditional Indian architectural features (e.g., central open courtyards / *Thotti Mane*) are approximated via procedural room templates.
3. **2.5D Elevation Extrusion**: The 3D model is rendered via 2.5D parametric extrusion of 2D vector coordinates rather than full BIM / IFC volumetric modeling.
